# 뉴스 신호 백테스트 — 「뉴스 신호가 수익을 예측하는가」 — 설계 v1 (2026-09-12)

> 사장님 결정(2026-09-12 브레인스토밍 3문답): 목적 = **뉴스 신호가 수익을 예측하는가**(매매 전략 튜닝이 아니다) · 신호 창 = **생산 창과 섹터 창을 둘 다 돌려 비교** · 접근 = **스냅샷 재현형**(생산 코드를 과거 시점으로 돌린다).
> 인수 메모의 우선순위 `0 원장 → 1 감성버그 → 2 종목추출 → 3 DART 시각 → 4 백테스트` 의 **4번**이다. 0~3 은 완료됐고, 그 수정들이 이 백테스트의 전제조건이었다(§0).

---

## 0. 사실 (2026-09-12 실측)

DB 직접 조회와 코드 확인으로 검증한 것만 적는다.

### 0.1 신호 원장은 백테스트에 못 쓴다

- `newsquant_signal_ledger` **359행**, `as_of` 가 전부 `2026-09-11` — 하루치다. 원장은 어제 만들어졌다(커밋 `e856bcf`).
- ⇒ 과거 신호를 **`news` 에서 재구성**해야 한다. 이것이 이 설계의 출발점이다.

### 0.2 재구성의 재료는 낡았다

- `news` **211,197행** · `2024-12-23 ~ 2026-09-12` · `sentiment_score` 채움률 100% · `related_stocks` 53.4%.
- 그런데 저장된 `related_stocks` 는 **어제 고친 그 추출기**(커밋 `b75de2a`)가 만든 값이다. 같은 본문 4,000건에 구·신 코드를 각각 돌려 비교하면 **기사 1,619건(40%)** 의 결과가 바뀐다(제거 1,109 / 추가 3,722).
- 저장된 `sentiment_score` 도 구 로직이다(인수 메모: 표본상 5.9% 변경 · 3.5% 부호 반전).
- ⇒ 저장된 값으로 백테스트하면 **이미 고친 버그가 섞인 과거 파이프라인**을 측정하게 된다.

### 0.3 재처리 비용은 작다

실측(300건 표본 → 211,197건 환산, 단일 스레드):

| 단계 | 1건당 | 211,197건 |
|---|---|---|
| 감성 분석 `SentimentAnalyzer.analyze_news` | 0.3 ms | **0.9 분** |
| 종목 추출 `extract_stock_codes` | 9.43 ms | **33.2 분** |

### 0.4 가격 데이터는 충분하다

- `daily_prices` **3,200,417행** · `2021-01-04 ~ 2026-09-11` · 2,799 종목.
- 컬럼 형식 주의: `date` 는 **TEXT `YYYY-MM-DD`**(10자), `stock_code` 는 `character(6)`.
- 뉴스가 붙은 (뉴스일, 종목) 조합 54,591건 중 **90.9%** 에 당일 가격이 있다.
- 백테스트 가능 거래일: `2026-01-07 ~ 2026-09-11` 기준 **169일**.

### 0.5 수익 컬럼은 수정주가가 아니다

- `returns_1d` = `(close - prev_close) / prev_close` 의 **소수**다. 2026-08-01~09-11 구간 77,073건이 **전부 정확히 일치**(오차 < 0.0001).
- 즉 **액면분할·병합을 반영하지 않는다**. `adj_factor` 는 2026년 438,583행 중 292,503행(66.7%)만 채워져 있어 기댈 수 없다.
- 한국거래소 일간 가격제한폭은 ±30% 다. 따라서 **`|returns_1d| > 0.30` 은 정의상 수익이 아니라 기업행위**다. 2026년 430,912건 중 **441건(0.102%)** 뿐이다.

### 0.6 시장지수는 이 기간을 못 덮는다

- `market_index` : `KOSPI` 등 1,255행씩, 2021-01-04 부터 **2026-02-12 에서 끊긴다**.
- `index_daily` : `KOSPI`·`KOSDAQ` 63행씩, **2026-06-15 부터** 2026-09-11 까지.
- ⇒ 169 거래일 중 **2026-02-13 ~ 06-14 약 4개월이 빈다**. 지수 대비 초과수익은 계산할 수 없다.

### 0.7 생산 신호의 정의

`TradingAnalyzer.analyze_today_stocks()` (`news_scraper/trading_analyzer.py`):

```
composite_score = adjusted_sentiment*0.35 + avg_overall*0.35 + news_score*0.15 + volume_adj*0.15
news_score      = min(news_count / 10.0, 1.0)
```

- 뉴스 창은 **달력 하루** `today 00:00:00 ~ 23:59:59` (`trading_analyzer.py:39-41`).
- `adjusted_sentiment` ← `_adjust_for_price_reaction(sentiment, stock_code, days=3)` (`:358`). **최근 종가 vs 3일 전 종가**를 보고 「이미 반영됐으면 하향」한다. 지금은 `self.price_fetcher.get_daily_price()` 로 **종목당 HTTP 1회**를 쏜다(`:375`).
- 원장 스냅샷 시각 `SIGNAL_LEDGER_TIMES = ((9,5), (10,0), (14,0), (15,20), (15,40))`, 주석에 「15:40 이 장 마감 직후 **결정 시각**」.

### 0.8 창 규약이 두 갈래다

- 섹터 집계 `compute_window` : `(직전 평일 15:30, now]`. 주석 — 「D-1 장중 뉴스는 D-1 종가에 반영됐다고 보고 뺀다」. `FREEZE_FROM = 09:05`, 주석 — 「**봇이 09:00 에 읽은 값** 보존」.
- 종목 신호 `analyze_today_stocks` : **달력 하루**(§0.7).
- ⇒ 종목 신호는 **D-1 장 마감 후 뉴스를 통째로 버린다.** 09:05 스냅샷 시점에 보이는 것은 D 00:00~09:05 뉴스뿐이고, 밤사이 쏟아진 재료가 빠진다. DART 공시가 바로 거기 몰린다(커밋 `91d4d83`: 수집 시각 기준 15:30 이후 접수분이 40.5%).

### 0.9 기존 평가 스크립트는 죽어 있다

- `scripts/evaluate_ai_prediction.py` 는 `sqlite3.connect("news_data.db")` 로 읽는다. PostgreSQL 이관(2026-08-16) 이후 동작하지 않는다. 재사용하지 않는다.

## 1. 결정 사항 (🔒 = 사장님 결정)

1. 🔒 **목적은 측정이다.** 「뉴스 신호가 다음 수익을 예측하는가」에 IC·분위수 수익으로 답한다. 매매 전략 튜닝·체결비용·포지션 사이징·슬리피지는 **범위 밖**이다.
2. 🔒 **신호 창은 둘 다 돌린다.** `as_of` 를 **D 09:00** 으로 고정하고(§5.3) 창의 «시작점»만 바꾼다.
   - (a) `prod_calendar` = **`[D 00:00, D 09:00]`** — 생산 코드의 달력 하루 창을 `as_of` 에서 자른 것. 09:05 스냅샷이 실제로 보는 범위와 같다.
   - (b) `sector_1530` = **`(D-1 15:30, D 09:00]`** — 섹터 집계 규약.
   차이는 **D-1 장 마감 후 ~ D 자정 사이 뉴스를 넣느냐 빼느냐** 하나뿐이다. 같은 엔진에 창만 바꿔 넣어 「창 선택이 예측력에 얼마나 기여하는가」를 추측 없이 수치로 답한다.
3. 🔒 **접근은 스냅샷 재현형이다.** `TradingAnalyzer` 에 시계와 가격 조회를 주입 가능하게 만들어 **생산 코드를 그대로** 과거 시점으로 돌린다. 신호와 백테스트가 갈라질 수 없게 하는 것이 목적이다.
4. 🔒 **재처리 결과는 `news` 를 덮지 않는다.** 별도 테이블에 쌓는다. 원본을 보존해야 재처리 로직이 또 바뀌었을 때 다시 만들 수 있고, DART 백필(`6978b7c`)처럼 운영 테이블을 또 건드리지 않아도 된다. 인수 메모의 「감성 21만 백필」과는 **분리한다** — 백테스트는 파생 테이블만 읽는다.
5. **진입은 D 시가**다. 봇이 09:00 에 읽고 개장에 매매하는 규약(§0.8)과 맞춘다. 청산은 **D 종가 · D+1 종가 · D+5 종가** 세 구간을 모두 잰다.
6. **초과수익은 일별 횡단면 평균 차감**으로 구한다. 지수가 4개월 비어 있고(§0.6), IC 는 순위상관이라 어차피 횡단면이며 시장중립이다. **없는 데이터에 기대지 않는다.**
7. **`|일간수익| > 0.30` 관측은 버린다.** 기업행위다(§0.5). 버려지는 양은 0.102% 다.
8. **순열 검정 대조군을 반드시 같이 돌린다.** 169 거래일은 IC 유의성에 넉넉한 표본이 아니다. 「IC 0.03」이 우연과 구별되는지 숫자로 말할 수 있어야 한다.
9. **미래 참조 차단에 테스트를 건다.** 백테스트가 가장 쉽게, 가장 조용히 틀리는 지점이다.

## 3. 구조와 데이터 흐름

```
news (원본 텍스트 211,197건)
  │
  ├─ ① 재처리 ──────────→ news_reprocessed
  │     현재 코드로 related_stocks · sentiment_score · overall_score 재계산
  │
  ├─ ② 신호 재현 ───────→ backtest_signal
  │     거래일 D × 창2종 × 종목 → composite_score
  │     (생산 TradingAnalyzer 를 과거 시점으로, 가격은 daily_prices 어댑터)
  │
  ├─ ③ 수익 결합 ───────  daily_prices (진입 D 시가 / 청산 D·D+1·D+5 종가)
  │
  └─ ④ 측정 ────────────→ 리포트 (IC · 분위수 수익 · 히트율 · 순열 검정)
```

각 단계는 앞 단계의 산출물만 읽는다. ①은 33분짜리 배치라 한 번 만들어 두고 ②~④를 반복한다.

## 4. ① 재처리 — `news_reprocessed`

현재 코드로 `news` 전체를 다시 돌려 파생 테이블에 쌓는다.

| 컬럼 | 출처 |
|---|---|
| `news_id` | `news.news_id` (PK) |
| `published_at` | `news.published_at` (DART 는 `91d4d83`·`6978b7c` 로 이미 고쳐졌다) |
| `source`, `title` | 그대로 |
| `related_stocks` | `BaseCrawler.extract_stock_codes(title + ' ' + content)` 재계산 |
| `sentiment_score` 외 점수들 | `SentimentAnalyzer.analyze_news()` 재계산 |
| `code_version` | 재처리 시점의 `git rev-parse --short HEAD` |
| `reprocessed_at` | 실행 시각 |

- `code_version` 을 남기는 이유: 이 테이블은 「어느 시점 코드의 출력인가」가 곧 의미다. 이게 없으면 나중에 결과를 볼 때 무엇을 측정한 건지 알 수 없다.
- 스크립트는 **기본 dry-run**, `--apply` 로만 쓴다. `scripts/backfill_dart_published_at.py` 와 같은 관례를 따른다.
- 재실행 안전: `news_id` 기준 UPSERT.

> **주의** — 인수 메모가 지적한 대로 `scripts/reprocess_data.py` 는 쓸 수 없다. 점수 있는 행을 스킵하고, 대상이 오늘로 하드코딩돼 있고, 본문 크롤링과 한 루프라 `sleep 1.5s` 가 있고, **`overall_score` 가중치가 본체와 다르다**(0.5/0.2/0.2/0.1 vs `analyze_news` 의 0.4/0.3/0.2/0.1). 새로 쓴다.

## 5. ② 신호 재현 — point-in-time `TradingAnalyzer`

### 5.1 지금 왜 과거로 못 돌리는가

- `analyze_today_stocks()` 가 `datetime.now()` 에 직접 묶여 있다(`:39`).
- `_adjust_for_price_reaction()` 이 `self.price_fetcher` 로 **실시간 HTTP** 를 쏜다(`:375`).

### 5.2 바꿀 것

1. **뉴스 창을 인자로 받는다.** `analyze_today_stocks()` 는 「창을 계산해 내부 메서드에 넘기는 얇은 껍데기」가 된다. 생산 경로는 지금과 **한 글자도 다르지 않게** 동작해야 한다(§9 동치성 테스트).
2. **가격 조회를 주입한다.** `PriceFetcher` 와 같은 인터페이스를 갖되 `daily_prices` 를 `as_of` 이전까지만 읽는 어댑터를 만든다. 생산 경로는 기존 `PriceFetcher` 를 그대로 쓴다.
3. 부수 효과: 미뤄둔 성능 과제 **「`_adjust_for_price_reaction` 종목당 HTTP 1회 — 359종목 27초」** 가 여기서 같이 풀린다. 어댑터는 종목 전체를 한 번에 읽어 캐시한다.

### 5.3 산출물 `backtest_signal`

거래일 D(169일) × 창 2종 × 그날 뉴스가 붙은 종목:

`trade_date`, `window_kind`(`prod_calendar` / `sector_1530`), `as_of`, `stock_code`, `news_count`, `avg_sentiment`, `adjusted_sentiment`, `avg_overall`, `volume_signal`, `composite_score`, `code_version`

`as_of` 는 **D 09:00** 으로 고정한다(§0.8 의 「봇이 09:00 에 읽는다」).

## 6. ③ 수익 결합

- **진입** : D 시가 `daily_prices.open`.
- **청산** : D 종가 / D+1 종가 / D+5 종가. 세 구간을 모두 계산해 리포트에 나란히 둔다.
- **수익** : `(청산가 - 진입가) / 진입가`.
- **필터** : 진입일~청산일 사이 어느 하루라도 `|returns_1d| > 0.30` 이면 그 관측을 버린다(§0.5, 결정 7).
- **초과수익** : 같은 거래일·같은 청산구간의 **횡단면 평균을 뺀다**(결정 6).
- 조인 주의(§0.4): `daily_prices.date` 는 TEXT `YYYY-MM-DD`, `stock_code` 는 `character(6)`. `to_char(d,'YYYY-MM-DD')` 와 `trim()` 을 쓴다. **이 형식을 틀리면 조인 결과가 조용히 0행이 된다** — 설계 중 실제로 겪었다.

## 7. ④ 측정 지표

| 지표 | 정의 | 읽는 법 |
|---|---|---|
| **IC** | 거래일마다 `composite_score` × 이후 초과수익의 **스피어만 순위상관**. 일별 IC 시계열의 평균과 t통계량 | **핵심 숫자.** 평균 IC 가 0 과 유의하게 다른가 |
| **분위수 수익** | 일별 `composite_score` 5분위, 각 분위의 평균 초과수익 | **단조성**이 있는가. Q5−Q1 스프레드 |
| **히트율** | 상위 N종목의 초과수익 > 0 비율 | 방향이 맞는 빈도 |
| **표본 수** | 일별 종목 수 · 전체 관측 수 | 결론의 신뢰도. **항상 같이 보고한다** |

- **순열 검정**(결정 8): 거래일 안에서 점수를 무작위로 섞어 같은 절차를 N회 돌리고, 실제 평균 IC 가 그 분포의 어디에 있는지 본다.
- **자기상관 한계**: 일별 IC 는 독립이 아니다. 단순 t검정 결과를 보고하되 그 한계를 같이 적는다. Newey-West 는 이번 범위 밖.
- 출력은 창 2종을 **나란히** 둔다(결정 2).

## 8. 미래 참조 차단과 한계

**차단**

- 뉴스: `published_at <= as_of` 로만 조회한다. **DART 시각을 고쳤기 때문에 이 조건이 비로소 의미를 갖는다** — 고치기 전이었다면 공시가 전부 자정이라 하루 종일의 뉴스가 새벽부터 존재한 것처럼 보였을 것이다(`91d4d83`).
- 가격: `_adjust_for_price_reaction` 은 `date < D` 종가까지만 본다.
- 수익: 진입 시가 이후의 가격만 청산에 쓴다.

**한계 (리포트에 명시한다)**

1. **생존 편향** — 종목 사전이 현재 시점 기준이라 상장폐지 종목이 빠져 있다. 나쁜 뉴스의 극단 사례가 사라지는 방향이라 **결과를 낙관적으로 만든다**.
2. **수정주가 부재** — ±30% 필터로 기업행위를 걸러내지만, 30% 이내의 소규모 기업행위는 남는다(§0.5).
3. **표본 169 거래일** — 짧다. 순열 검정과 표본 수 보고로 보완하되, 이 한계는 사라지지 않는다.
4. **`related_stocks` 오탐은 재처리 후에도 남는다** — 어제 수정으로 크게 줄었지만 0 은 아니다(`b75de2a`).

## 9. 테스트

미래 참조는 조용히 틀리므로 거기에 테스트를 집중한다.

1. **point-in-time 뉴스 조회** — 합성 뉴스로, `as_of` 이후 `published_at` 을 가진 뉴스를 **절대 반환하지 않는다**.
2. **가격 어댑터** — 합성 가격으로, `as_of` 이후 종가를 **절대 반환하지 않는다**.
3. **생산 경로 동치성** — 리팩터링 후 `analyze_today_stocks()` 가 리팩터링 전과 같은 결과를 낸다. 종목 추출 때 쓴 골든 픽스처 방식을 그대로 쓴다.
4. **IC·분위수 계산** — 알려진 입력에 알려진 값. 완전 상관 입력에 IC = 1, 무상관 입력에 IC ≈ 0.
5. **기업행위 필터** — ±30% 초과 관측이 제거된다.
6. **조인 형식** — TEXT `YYYY-MM-DD` 와 `character(6)` 조인이 0행을 내지 않는다(§6 의 실제 사고 재발 방지).

DB 가 필요한 테스트는 `pytest.mark.db` + 센티널 관례를 따른다(`tests/test_dart_backfill.py` 참조).

## 11. 실행 순서

1. `TradingAnalyzer` 주입 리팩터링 + 동치성 골든 (생산 동작 불변 확인)

6. 리포트 판독 — **IC 가 0 과 구별되지 않으면 그렇게 보고한다.** 신호가 예측력이 없다는 것도 답이다.
